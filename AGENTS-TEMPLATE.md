# Project instructions

Замени все placeholders фактическими значениями проекта и удали неприменимые пункты. ## Границы изменений

- Основная конфигурация: `<read-only либо разрешено изменение>`.
- Если основная конфигурация read-only, прикладные изменения выполнять в согласованном расширении `<ExactExtensionName>`.
- Правки BSL и добавление методов в существующие модули в рамках согласованной задачи выполнять самостоятельно с проверками по `.opencode/rules/verification.md`.
- После любой правки выполнять внутреннюю самопроверку по `.opencode/rules/verification.md`, исправлять найденные относящиеся к задаче проблемы и повторять проверку после исправлений.
- Перед итоговым ответом обязательно выполнить ревью совокупности изменений текущей задачи по `.opencode/rules/verification.md`; найденные относящиеся к задаче проблемы исправить и повторить затронутые проверки и ревью.
- До создания или изменения структуры метаданных, добавления индекса, подписки на событие или регламентного задания, изменения режима совместимости или блокировок согласовать решение, если оно ещё не согласовано в задаче.
- Аналогично согласовать перехват часто вызываемого метода в расширении и применение `ОбменДанными.Загрузка = Истина`; ответственность за целостность описана в `.opencode/rules/coding-standards.md`.
- Тесты создавать и запускать только по явному запросу пользователя. Если при запросе создания не указаны сценарии, методы покрытия или количество, сначала уточнить требования; не выбирать состав и число тестов самостоятельно. Общие требования — `.opencode/rules/testing.md`.
- Перед загрузкой конфигурации/расширения в базу получать подтверждение пользователя.
- Не удалять, не сбрасывать и не перезаписывать несвязанные пользовательские изменения.

## MCP

### 1C MCP Toolkit (Опциональный, при доступности)

#### Основные сценарии

#### 1. Уточнение структуры фактической базы

Инструмент: `get_metadata`.

Использовать, когда нужно:
- проверить наличие справочника, документа или регистра;
- узнать реальные реквизиты и табличные части;
- подготовить корректный запрос;
- сравнить структуру базы с XML-исходниками;
- проверить, загружены ли ожидаемые объекты конфигурации.

Важно: структура базы не доказывает, что в неё загружена последняя версия XML проекта.

---

#### 2. Получение фактических данных

Инструмент: `execute_query`.

Примеры:
- проверить наличие документов или элементов справочника;
- получить остатки и обороты;
- оценить количество обрабатываемых записей;
- найти данные, на которых воспроизводится ошибка;
- проверить состояние данных до или после операции;
- оценить масштаб планируемой миграции.

Перед каждым запросом необходимо показать пользователю:
- цель;
- целевую базу;
- точный текст запроса и параметры;
- ограничения периода и объёма;
- возможную нагрузку.

Запрос выполняется только после отдельного подтверждения.

---

#### 3. Подготовка плана миграции или обработки данных

Последовательность:
1. `get_metadata` — подтвердить структуру.
2. `execute_query` — оценить количество и состояние данных.
3. Определить граничные случаи и ожидаемые изменения.
4. Составить план обработки, проверки и восстановления.
5. При реализации — отдельно согласовать `execute_code`.
6. Повторным `execute_query` проверить результат.

---

#### 4. Создание или изменение данных

Инструмент: `execute_code`.

Применять только:
- в подтверждённой dev/test базе;
- в режиме реализации, но не планирования;
- после показа точного кода;
- после описания изменяемых данных;
- при наличии способа проверить и при необходимости компенсировать результат;
- после отдельного подтверждения каждого вызова.

Примеры:
- создать тестовые данные;
- исправить данные;
- выполнить согласованную миграцию;
- воспроизвести сценарий через создание объекта;
- очистить специально созданные тестовые данные.

Для продуктивной или неопределённой базы `execute_code` не используется.

---

#### 5. Диагностика ошибки по журналу регистрации

Инструмент: `get_event_log`.

Использовать, чтобы:
- найти исключение после воспроизведения ошибки;
- проверить события записи или проведения;
- изучить ошибки фонового задания;
- определить пользователя, сеанс и момент операции;
- диагностировать таймаут или неопределённый результат.

Запрос журнала следует ограничивать:
- временным интервалом;
- типом события;
- объектом или операцией;
- уровнем важности;
- числом записей.

Отсутствие события в журнале не доказывает, что операция не выполнялась.

---

#### 6. Исследование конкретного объекта

Инструменты:

- `get_object_by_link`;
- `get_link_of_object`;
- `find_references_to_object`.

Использовать, когда нужно:

- получить объект по навигационной ссылке;
- сформировать ссылку для воспроизведения сценария;
- найти документы и записи, ссылающиеся на объект;
- оценить последствия удаления или изменения данных;
- исследовать связанную цепочку объектов.

Результаты могут содержать конфиденциальные данные, поэтому следует получать только необходимые поля.

---

#### 7. Уточнение синтаксиса BSL

Инструмент: `get_bsl_syntax_help`.

Подходит для:

- поиска методов и свойств платформенных типов;
- уточнения параметров функций;
- проверки доступных конструкций языка;
- получения краткой справки по BSL.

Разделение ответственности:

- `get_bsl_syntax_help` — справка по синтаксису;
- `bsl-language-server` — анализ конкретного кода проекта;
- skill `bsp` — API соответствующей версии БСП.


#### Ограничения использования

- Ограничивать период, область данных и объём результата; полное чтение таблицы требует отдельного обоснования. Лимит возвращаемых строк сам по себе не ограничивает стоимость выполнения запроса.
- Не запускать тяжёлые запросы параллельно. Клиентский timeout не гарантирует остановки запроса в 1С.
- Перед каждым `execute_query` получить отдельное подтверждение пользователя.
- В режиме планирования `execute_code` запрещён, в том числе для чтения. В режиме выполнения допустим только для явно подтверждённой dev/test базы; для продуктивной или неопределённой базы не использовать.
- Перед каждым `execute_code` показать целевую базу, точный код, создаваемые/изменяемые данные, ожидаемый результат, способ проверки и восстановления либо компенсации при ошибке; получить отдельное подтверждение именно этого вызова.
- Общее разрешение на разработку, прошлый вызов или сохранённый в OpenCode выбор `Allow always` не заменяют отдельного подтверждения каждого `execute_query` и `execute_code`. При изменении кода, запроса, параметров или базы согласовать вызов заново.
- Само наличие MCP не разрешает запуск тестов, запись/проведение, перезапуск или закрытие сеанса; границы задачи и согласования сохраняются.

### MCP bsl-language-server

#### Основные сценарии

#### 1. Перед написанием кода

Использовать для поиска уже существующей реализации:

1. Найти вероятный модуль через `grep`/`glob`.
2. Получить его структуру через `document_symbols`.
3. Проверить объявление через `definition` или `hover`.
4. Проверить использования через `find_references`.

Это помогает не создавать дублирующие методы.

#### 2. При составлении плана

Использовать, если решение зависит от:

- фактической цепочки вызовов;
- расположения бизнес-логики;
- существующего публичного API;
- количества потребителей изменяемого метода;
- клиентского или серверного контекста.

Например, перед изменением экспортной функции нужно выяснить, кто её вызывает и какие пути выполнения будут затронуты.

#### 3. После изменения BSL

В текущих правилах проекта для каждого изменённого `.bsl` требуется:

1. Запустить `analyze_file` после последней правки.
2. Обработать связанные с изменением ошибки и значимые диагностики.
3. После исправления повторить анализ.
4. Для изменённого экспортного метода дополнительно выполнить `find_references`.
5. При изменении сигнатуры или поведения — `call_hierarchy`.

#### Ошибки MCP

- Если вызов MCP завершился ошибкой таймаута (`Request timed out`), повторить тот же вызов с теми же параметрами.
- Выполнять не более трёх попыток суммарно: первоначальный вызов и два повтора. После успешного ответа прекратить повторы.
- Повторять вызов только после получения ошибки предыдущей попытки; не запускать одинаковые запросы параллельно.
- Если все три попытки завершились ошибкой, сообщить об этом пользователю. Для проверки указать статус «не проверено — MCP вернул ошибку после трёх попыток».
