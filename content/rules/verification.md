# Проверка изменений

Проверяется последнее сохранённое состояние. Содержательная правка делает относящийся к ней результат устаревшим. Не повторять проверку неизменённого содержимого без новой причины. Статусы проверок, серьёзность замечаний и решения ревью — по `.opencode/glossary.md`.

## Режим работы

- При реализации обязательны три этапа: самопроверка после правок, применимые инструментальные проверки и итоговое ревью совокупности изменений задачи перед ответом пользователю. Отдельный запрос на них не нужен.
- При отдельном ревью по явному запросу только читать и анализировать: не исправлять, не форматировать, не загружать исходники в базу и не менять окружение. До начала получить точную область и цель: diff, список файлов или готовое архитектурное решение. Если область отсутствует или неоднозначна, уточнить её; не угадывать состав изменений по рабочему дереву.
- Для ревью прочитать `.opencode/rules/source-search.md` и применимые правила по артефактам согласно корневому `AGENTS.md` с их `depends_on`; для BSL — `coding-standards.md`, для архитектурного решения или изменения структуры метаданных — `architecture.md`. Остальные правила не загружать.
- Инструменты использовать для подтверждения фактов. Ограничения текущего режима и разрешений имеют приоритет над рекомендацией запустить инструмент; недоступная проверка получает статус `не проверено — причина`. Skill не расширяет разрешения. При read-only ревью не запускать validators со скриптами, меняющими файлы или окружение, DB-операции и runtime-сценарии.

## 1. Самопроверка после правок

- После любой правки самостоятельно проверить изменённый фрагмент и влияющий на него соседний код: стиль, читаемость, корректность, граничные случаи, безопасность и конкурентность. Для некодовых артефактов проверить применимые аспекты, согласованность правил, ссылок и примеров.
- Дополнительно проверить права, контекст выполнения, публичный контракт и транзакционные границы, если правка их затрагивает. Не ограничиваться отсутствием диагностик анализатора.
- Найденные относящиеся к задаче проблемы исправить и повторить самопроверку после исправлений. Продолжать цикл, пока в затронутом коде не останется выявленных проблем; повторить применимые инструментальные проверки последнего состояния.
- Непроверенные аспекты и остаточные риски явно указать. Не считать самопроверку доказательством отсутствия всех ошибок и не исправлять попутно несвязанные пользовательские изменения.

## 2. Инструментальные проверки

### BSL

Для каждого изменённого `.bsl`:

1. Вызвать `analyze_file` после последней правки.
2. Обработать синтаксические ошибки и связанные с изменением диагностики важности `BLOCKER`, `CRITICAL`, `MAJOR` в изменённых строках или затронутом пути. Несвязанные старые диагностики не исправлять попутно; остальные перечислить с решением/обоснованием.
3. Не путать важность диагностики BSL LS с числом LSP severity. Если MCP возвращает только LSP severity, отдельно обработать все ошибки, а важность прочих подтвердить по метаданным диагностики; неизвестную важность явно отметить.
4. После исправления повторить анализ затронутого файла. Новые относящиеся к изменению ошибки также устранить и проверить; не ограничивать число итераций ценой незамеченной ошибки.
5. Проверить литералы `\t`, `\n`, `\r`, отсутствие `ё/Ё` (U+0451/U+0401) и длинного тире (U+2014) во всём содержимом изменённого `.bsl` по `coding-standards.md`. Проверить изменённый код на `Сообщить()`, чтение реквизитов ссылок через точку, необоснованный перехват ошибок БД, конкатенацию значений в запросах и цепочки вызовов от `Запрос.Выполнить()`. Совпадения поиска оценивать по контексту, а не заменять механически.
6. Для изменённого экспортного метода проверить `find_references`; при изменении сигнатуры, результата, побочных эффектов или отказа обязательно проверить `call_hierarchy` и динамические точки входа по `source-search.md`.


Анализ влияния нужен также при удалении/переименовании, изменении подписки, задания, RLS и транзакционного пути. Проверить прямые, строковые и платформенные точки вызова.

### XML и метаданные

- Загрузить профильный skill: `meta-validate`, `form-validate`, `role-validate`, `skd-validate`, `mxl-validate`, `subsystem-validate`, `interface-validate`, `xdto-validate`, `cfe-validate`, `cf-validate`, `erf-validate` или `epf-validate`.
- Расширение проверять вместе с точной основной конфигурацией.
- Проверить регистрацию объекта в родительских XML, права, включение в подсистему и командный интерфейс по `metadata.md`, если они затронуты. Для неприменимого пункта указать причину.
- Не считать визуально корректный XML прошедшим проверку. После последующей XML-правки повторить профильную проверку.
- Для формы различать корректность XML, открытие платформой и пользовательский сценарий; для отчёта/печати — структуру и фактический результат.

### Необязательный платформенный контроль

Предложить, когда изменены директивы компиляции, вызовы платформенного API, заимствования расширения либо статический анализ не снимает сомнение. Перед подключением к dev-базе получить подтверждение состава операции и проверить, что проверяется последняя версия исходников; отдельную загрузку согласовать по `AGENTS.md`.

- Для расширения — skill `db-cfe-admin`, операция `check`, параметры `-Name <имя> -Checks modules` и нужные контексты компиляции. Проверку применимости (`apply`) учитывать отдельно.
- `db-cfe-admin check` не проверяет основную конфигурацию. Для неё использовать синтаксический контроль Конфигуратора с параметрами, подтверждёнными документацией установленной платформы; при отсутствии подходящего skill описать точное ручное действие и критерий результата.
- Сохранить код завершения, лог, проверенные контексты, версию платформы и соответствие исходникам. Успех на сервере не доказывает компиляцию веб-клиента.

## Критерии ревью

- Для кода проверять функциональные ошибки, контексты выполнения, `NULL`/`Неопределено`, граничные случаи, права, транзакционные границы, конкурентность, безопасность, производительность, публичные контракты и регрессии API.
- Для архитектуры проверять границы компонентов, модель данных, интеграции, права, конкурентность, совместимость, тестируемость и возможность отката. Для некодовых артефактов — согласованность правил, ссылок, маршрутов и примеров.
- Включать в замечания только подтверждённые ошибки: указывать `path:line` или компонент решения, доказательство и наблюдаемое последствие. Низкоуверенные предположения перечислять как проверочные вопросы или остаточные риски, а не подтверждённые замечания.
- Имена и форматирование отмечать, если нарушено явное правило проекта, сломан контракт/маршрут или существенно затруднено понимание изменённой логики. Косметические предпочтения и несвязанный старый код не включать.
- Не ревьюить сгенерированный/vendor-код, исходники YAxUnit, локальные настройки и артефакты сборки, если они не входят в область задачи или явно запрошенного ревью.
- Не требовать новую архитектуру и тесты вне задачи только ради общего улучшения. Недостающую проверку, необходимую для вывода, оформить как следующий шаг.

## Результат

При завершении реализации кратко указать результат итогового ревью, выполненные проверки, непроверенные аспекты и остаточные риски. Не выводить полный шаблон отдельного ревью без необходимости.

При отдельном ревью по явному запросу не исправлять найденное; оформить результат так:

```markdown
## Результат ревью
**Область:** ...
**Решение:** одобрено / есть замечания / блокирующие замечания

### блокирующее|критичное|важное|незначительное — Заголовок
**Место:** `path:line` или компонент
**Уверенность:** высокая/средняя
**Доказательство:** ...
**Последствие:** ...
**Исправление / следующая проверка:** ...

## Выполненные проверки
- ...

## Остаточные риски
- ...
```

Для каждой проверки указать инструмент, артефакт/сценарий, контекст и результат: `проверено`, `ошибка` или `не проверено — причина`. Непроведённые проверки не позволяют утверждать полную готовность решения. Не утверждать «всё проверено», если часть применимых уровней отсутствовала.
